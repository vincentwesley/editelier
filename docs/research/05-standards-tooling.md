# 05 — Professional standards, testing and Claude Code tooling

Research date: 2026-11-25. Scope: Editelier (Tauri 2, Rust core, TS webview UI, wgpu, Media Foundation + LGPL FFmpeg, Windows). Read-only research: nothing was installed. Every factual claim links its source; lines marked **Rec:** are our engineering recommendations built on those sources.

---

## A. Professional standards

### A1. Frame-accurate timing

**Rational time, never floats.**
- OpenTimelineIO models time as `value` at `rate` (seconds = value × 1/rate), rescalable to other rates, with exclusive range ends ([OTIO opentime API](https://opentimelineio.readthedocs.io/en/latest/api/python/opentimelineio.opentime.html)). Floating-point maths makes precise frame navigation "difficult, if not impossible" ([WHATWG thread, Apple engineer](https://lists.w3.org/Archives/Public/public-whatwg-archive/2012Oct/0013.html)); see also [The Rational Rationale (vtc)](https://hexdocs.pm/vtc/the_rational_rationale.html).
- **Rec:** core type `Time { num: i64, den: u32 }` (or ticks at a per-stream timebase, as FFmpeg's `AVRational` does). Sequence time = rational at the project rate (e.g. 30000/1001). Convert each source stream's PTS (in its own timebase) into sequence time with exact integer rescale (round-to-nearest, documented tie rule). Floats only at the UI/render edge. Keep ranges half-open like OTIO.

**PTS handling, edit lists and B-frames.**
- MP4 edit lists (`elst`) shift presentation start, for example to compensate for 2 B-frames of reorder delay; FFmpeg had seek inaccuracy matching that offset ([trac #6315](https://trac.ffmpeg.org/ticket/6315)). FFmpeg's demuxer now locates edit-list starts by media time and drops decoded frames outside the edit boundaries ([2017 cvslog commit](https://ffmpeg.org/pipermail/ffmpeg-cvslog/2017-November/110616.html)).
- AAC has 1024 priming samples that are discarded via the edit list ([trac #6315 discussion](https://trac.ffmpeg.org/ticket/6315)); fragmented MP4 after the first fragment has ignored the edit list, duplicating/dropping priming and offsetting PTS by 1–2 frames ([trac #9372](https://fftrac-bg.ffmpeg.org/ticket/9372)). Start-PTS shifts with/without edit lists remain an open topic ([trac #11034](https://trac.ffmpeg.org/ticket/11034)); browsers disagree on the same file ([Mozilla bug 2056945](https://bugzilla.mozilla.org/show_bug.cgi?id=2056945)).
- YouTube asks for MP4 with **no edit lists** and moov atom at the front ([YouTube upload settings](https://support.google.com/youtube/answer/1722171)).
- **Rec (decode):** seek = demuxer seek to keyframe ≤ target (backward flag), then decode forward discarding frames until `pts >= target`; never trust the first returned frame. Apply edit lists (FFmpeg does by default) and test both MF and FFmpeg paths against the same oracle (section B1). Cache per-file index (keyframe PTS list) on import.
- **Rec (encode):** write zero-based PTS, no edit lists, `+faststart`; B-frames allowed but closed GOP (YouTube spec: 2 B-frames, closed GOP of half the frame rate, [source](https://support.google.com/youtube/answer/1722171)). Account for audio encoder delay explicitly rather than via `elst` where possible.

### A2. Variable-frame-rate (VFR) footage

- Phone and screen recordings are often VFR; Pixel phones cannot be forced to CFR ([Blackmagic forum](https://forum.blackmagicdesign.com/viewtopic.php?p=1138018)); iPhone VFR causes A/V sync drift in third-party apps ([Apple Communities](https://discussions.apple.com/thread/256095059)).
- **Premiere:** detects VFR (Properties); offers "Preserve Audio Sync" (default, adds/drops frames) vs "Smooth Video Motion" (keeps every frame, may drift); Adobe recommends transcoding VFR to CFR before proxy/consolidate workflows, and points to Shutter Encoder or HandBrake when Media Encoder fails ([Adobe VFR FAQ](https://community.adobe.com/t5/premiere-pro/faq-variable-frame-rate-vfr-video/td-p/10348229)). Clips in a mismatched sequence are adapted to the sequence rate keeping playback speed ([Adobe: mixed frame rates](https://www.adobe.com/ph_en/learn/premiere-pro/web/mixed-frame-rates)).
- **Resolve:** handles VFR poorly; community fix is transcode to CFR first (HandBrake "Same as source + Constant Framerate"), test one clip, verify tracks/tags survived ([DaVinci Resolve Club guide](https://davinciresolveclub.com/davinci-resolve-variable-frame-rate/)). No official Blackmagic VFR statement was found.
- FFmpeg exposes `-fps_mode passthrough|cfr|vfr|auto` (replaces deprecated `-vsync`) ([commit](https://code.ffmpeg.org/Traneptora/FFmpeg/commit/3dc319587f5bb96905f5984262e036c58a756c8c)).
- **Rec:** *preserve* on the timeline (we already key everything by PTS, so VFR costs nothing at edit time): show a "VFR" badge on import (detect from PTS delta variance), map timeline frame N to the source frame with largest PTS ≤ t (sample-and-hold). *Conform* only at export to the sequence rate (CFR), audio as master clock. Offer an optional "Conform to CFR (lossless-intermediate)" action for users who want Resolve-style workflows. This beats Premiere/Resolve's UX for our audience.

### A3. Colour management

- **SDR delivery = BT.709** for primaries, transfer and matrix; YouTube converts unsupported spaces to BT.709 and **full range to limited range**; RGB matrix not recommended ([YouTube upload settings](https://support.google.com/youtube/answer/1722171)).
- **Rec.709 vs sRGB:** same primaries/white point; difference is the tone curve. BT.1886 defines the reference display EOTF as a 2.4 power based on measured black/white ([Wikipedia: BT.1886](https://en.wikipedia.org/wiki/ITU-R_BT.1886)). Windows/Android reportedly treat Rec.709 as sRGB EOTF and Apple uses ~1.961 effective gamma ([W3C CSS thread](https://lists.w3.org/Archives/Public/public-css-archive/2025Aug/0074.html); [Apple dev forum](https://developer.apple.com/forums/thread/113337)); Premiere's viewing-gamma choices exist because of exactly this ([Adobe FAQ: viewing gamma](https://community.adobe.com/t5/premiere-pro-discussions/faq-viewing-gamma-choices-explained/m-p/15110693)).
- **Matrices and range:** BT.601 (SD) and BT.709 (HD) use different Y'CbCr coefficients; limited range puts Y' at 16–235 and chroma at 16–240 in 8-bit ([Wikipedia: YCbCr](https://en.wikipedia.org/wiki/YCbCr); [Wikipedia: Rec. 709](https://en.wikipedia.org/wiki/Rec._709)).
- **Linear-light blending in wgpu:** `*UnormSrgb` formats convert sRGB storage to linear floats in the shader automatically ([wgpu colour docs](https://wgpu.rs/doc/wgpu/documentation/color/srgb/index.html)); wgpu ships an `srgb_blend` example over sRGB/non-sRGB targets ([source](https://wgpu.rs/doc/src/wgpu_examples/srgb_blend/mod.rs.html)); `view_formats` lets one texture be viewed as sRGB or linear ([Learn wgpu 0.15 notes](https://sotrh.github.io/learn-wgpu/news/0.15)); sRGB views are not storage-bindable, so compute writes go through a non-sRGB view ([Mozilla bug 1977241](https://bugzilla.mozilla.org/show_bug.cgi?id=1977241); [LearnWebGPU colour issues](https://eliemichel.github.io/LearnWebGPU/next/appendices/color-space-issues.html)).
- **HDR phone footage (HLG/PQ):** detect via `color_transfer` = `arib-std-b67` (HLG) or `smpte2084` (PQ); common FFmpeg routes are zscale→linear→`tonemap` (hable/mobius/reinhard)→BT.709 retag, or GPU `libplacebo` with `bt.2390` ([2026 guide](https://dev.to/masonwritescode/ffmpeg-hdr-to-sdr-tone-mapping-that-doesnt-look-washed-out-2026-24ie); [ffmpeg-user thread](https://ffmpeg.org/pipermail/ffmpeg-user/2023-October/057044.html)). libplacebo has had a too-dark HDR10→709 regression ([issue 179](https://code.videolan.org/videolan/libplacebo/-/issues/179)).
- **HDR export (later):** YouTube HDR wants Rec.2020 NCL, PQ or HLG, 10/12-bit, VP9 Profile 2 / AV1 / HEVC, ST 2086 + MaxCLL/MaxFALL for PQ; SDR viewers get auto down-conversion or an embedded .cube LUT ([YouTube HDR](https://support.google.com/youtube/answer/7126552)).
- **Rec (pipeline):** decode → convert Y'CbCr to RGB on GPU using the *tagged* matrix + range (fallback heuristic: height ≤ 576 → 601, else 709; untagged phone HDR → read side data) → linearise (BT.1886/sRGB inverse, or HLG/PQ inverse + tonemap BT.2390 in our own WGSL) → **work in linear-light Rec.709 f16** (`Rgba16Float`) for all blending, scaling and effects → encode once at output. Preview: present through an `*Srgb` swapchain (matches Windows treatment above); offer a "Rec.709 2.4" viewing toggle later. Export: always write explicit tags (`-color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv`, and MF `MF_MT_VIDEO_PRIMARIES/TRANSFER_FUNCTION/YUV_MATRIX/NOMINAL_RANGE`). Photos: sRGB in/out, honour embedded ICC (convert to linear 709/sRGB on load).

### A4. Audio

- **EBU R128:** programme loudness −23.0 LUFS, max true peak −1 dBTP in production, measured per ITU-R BS.1770 / EBU Tech 3341 ([EBU R128 (2014)](https://tech.ebu.ch/docs/r/r128-2014.pdf); [Tech 3343](https://tech.ebu.ch/docs/tech/tech3343.pdf)). R128 s2 (streaming) allows streaming at −23 with device-side adaptation and recommends true-peak limiting when targets are higher ([R128 s2](https://knowledgehub.ebu.ch/files/live/sites/tech/files/shared/r/r128s2.pdf)).
- **Streaming −14 LUFS:** Spotify normalises to −14 LUFS (BS.1770), advises staying below −1 dBTP (−2 dBTP for masters louder than −14) ([Spotify for Artists](https://support.spotify.com/artists/article/loudness-normalization/)). No official YouTube/TikTok/Instagram loudness target page was found; −14 LUFS is an industry convention for those, not a published platform spec.
- **Sample rate:** YouTube 48 kHz, AAC-LC/Opus, stereo 384 kbps ([YouTube](https://support.google.com/youtube/answer/1722171)); Instagram Reels 48 or 96 kHz stereo ([Instagram Help](https://help.instagram.com/1038071743007909)).
- **Crate:** `ebur128` is a pure-Rust port of libebur128, MIT, passes EBU Tech 3341/3342 tests, includes LRA and true-peak ([docs.rs](https://docs.rs/ebur128)). Alternative: `ebur128-stream` (streaming, zero-alloc, young) ([docs.rs](https://docs.rs/crate/ebur128-stream/0.2.0)).
- **Rec:** internal mix at 48 kHz f32; resample everything on import. Export "Normalize loudness" option: presets −14 LUFS / −1 dBTP (Social), −16 LUFS (podcast-ish), −23 LUFS / −1 dBTP (Broadcast R128); two-pass (measure with `ebur128` integrated + true peak, apply gain, then a true-peak limiter only if needed). Show integrated LUFS + true peak in the export dialog.

## B. Testing approach

### B1. FFmpeg as oracle
- `framemd5` writes a per-packet/frame MD5 whose primary use is regression testing, reproducible across platforms ([ffmpeg-formats manual](https://manpages.debian.org/trixie/ffmpeg/ffmpeg-formats.1.en.html); [framemd5 how-to](https://trac.ffmpeg.org/wiki/framemd5%20Intro%20and%20HowTo)).
- Exact frame count: `ffprobe -v error -count_frames -select_streams v:0 -show_entries stream=nb_read_frames` decodes the whole file; `-count_packets` is faster but packets ≠ frames; some containers (AVI) have miscounted ([ffmpeg-user 2021](https://lists.ffmpeg.org/pipermail/ffmpeg-user/2021-March/052346.html); [faster alternative](https://lists.ffmpeg.org/pipermail/ffmpeg-user/2021-March/052368.html); [2014 AVI case](https://lists.ffmpeg.org/pipermail/ffmpeg-user/2014-May/021285.html)).
- **Rec:** tests in Rust (`cargo test`, feature `oracle`) that (1) decode N frames via our MF and FFmpeg paths, hash raw planes, compare to `ffmpeg -f framemd5 -pix_fmt <same>`; (2) seek-accuracy matrix: for each fixture (CFR, VFR, B-frames, edit list, HEVC 10-bit, HLG) seek to 20 random frames, assert returned PTS equals `ffprobe -show_frames` PTS; (3) exports: assert `nb_read_frames`, duration, stream tags (`color_*`, sample rate) via ffprobe JSON. Pin the oracle FFmpeg build version in the test README.

### B2. VMAF / SSIM / PSNR
- FFmpeg `libvmaf` filter (libvmaf v2 API): `model=version=vmaf_v0.6.1`, `feature='name=psnr|name=float_ssim'`, `log_fmt=json`, `n_threads` ([filter docs](https://ayosec.github.io/ffmpeg-filters-docs/5.0/Filters/Video/libvmaf.html); [v2 update](https://ffmpeg.org/pipermail/ffmpeg-cvslog/2022-January/130710.html)). Upstream: [Netflix/vmaf](https://github.com/Netflix/vmaf).
- Thresholds: ~6 VMAF points ≈ 1 JND (Netflix contact, secondhand) ([Streaming Learning Center](https://streaminglearningcenter.com/blogs/finding-the-just-noticeable-difference-with-netflix-vmaf.html)); "93–100 transparent" / "95+ identical" are informal conventions ([blog](https://nenadlazic.github.io/blog/vmaf-introduction/); [Fora Soft](https://www.forasoft.com/learn/video-quality/articles-vqm/vmaf-explained)).
- **Rec:** export-quality gate: mean VMAF ≥ 93 and 1st-percentile (harmonic/min-pooled) ≥ 85 for "High" presets vs a lossless render of the same timeline; regression alarm if mean drops > 2 points vs the stored baseline (well under 1 JND). Run only at milestones (slow).

### B3. Golden-frame image diff
- pixelmatch: perceptual per-pixel threshold 0–1 (default 0.1; Playwright uses 0.2), anti-alias detection, `windowSize` to ignore scattered noise ([pixelmatch](https://github.com/mapbox/pixelmatch); [Playwright note](https://camoa.github.io/dev-guides/testing/visual-regression/pixelmatch/)); Rust port exists ([crate](https://docs.rs/crate/pixelmatch/latest)).
- **Rec:** two tiers. (a) Deterministic CPU paths (colour conversion, LUT maths): exact or max |Δ| ≤ 1 code value per channel. (b) GPU renders (driver variance): read back `Rgba16Float`/`Rgba8`, compare with per-pixel max Δ ≤ 2/255 on ≥ 99.9 % of pixels **and** SSIM ≥ 0.995 per frame; store goldens per backend (D3D12/Vulkan) only if they genuinely differ. Always render goldens offscreen (no swapchain), fixed seed, fixed resolution.

### B4. Performance budgets on Windows
- **PresentMon** (Intel, open source): ETW-based frame timing for DX9–12/Vulkan/GL; `MsBetweenPresents` is submit cadence, `MsBetweenDisplayChange` is what reaches the screen ([GitHub](https://github.com/GameTechDev/PresentMon); [TechSpot explainer](https://www.techspot.com/article/2723-intel-presentmon/)).
- **Tracy** via `tracing-tracy` (gate behind its `enable` feature; pin client to GUI protocol version) ([tracing-tracy](https://docs.rs/crate/tracing-tracy/0.11.0); [tracy-client version table](https://docs.rs/crate/tracy-client/0.18.4)); GPU timing via `wgpu-profiler` (`tracy` feature, needs `TIMESTAMP_QUERY`) ([wgpu-profiler](https://docs.rs/crate/wgpu-profiler/0.15.0)).
- **PIX** timing captures combine CPU+GPU on D3D12 and can be triggered programmatically ([Microsoft Learn](https://learn.microsoft.com/en-gb/windows/win32/direct3dtools/pix/pix-timing-captures)). **WPR/WPA** for system-wide ETW (decode, disk, MF) ([Windows Performance Recorder](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/windows-performance-recorder)).
- **Rec:** `tracing` spans everywhere (zero-cost when off); headless bench binary (`cargo bench`/custom harness) that plays a fixed 4K timeline offscreen and records p50/p95/p99 frame time + decode latency into `budgets.json`; CI-free, run locally at milestones. Budgets to start: 1080p30 preview p95 ≤ 16 ms render, scrub-to-frame ≤ 100 ms (keyframe-local) / ≤ 250 ms (long GOP), cold import of 1 h file ≤ 2 s to first frame. PresentMon + PIX only for investigation, not gating.

### B5. tauri-driver / WebDriver E2E on Windows
- Desktop WebDriver via `tauri-driver` works on **Windows and Linux only**; macOS has no WKWebView driver ([Tauri WebDriver docs](https://v2.tauri.app/develop/tests/webdriver/)). msedgedriver must match the WebView2/Edge version or the suite can hang ([manual setup](https://v2.tauri.app/develop/tests/webdriver/manual-setup/); [tauri-driver](https://docs.rs/tauri-driver/)).
- WebdriverIO's Tauri service auto-detects the WebView2 version and downloads a matching msedgedriver (`autoDownloadEdgeDriver: true`), supports an `embedded` provider via `tauri-plugin-wdio-webdriver` registered debug-only, and lists the version-mismatch error and fix ([WDIO platform support](https://webdriver.io/docs/desktop-testing/tauri/platform-support); [Edge WebDriver on Windows](https://webdriver.io/docs/desktop-testing/tauri/edge-webdriver-windows)).
- Limitations: WebDriver sees only the DOM; our wgpu viewport is native, so pixel assertions must go through a debug command that returns a read-back frame hash (ties to section C3).
- **Rec:** WebdriverIO + `@wdio/tauri-service`, official provider on Windows, auto driver download; tests drive the TS UI and assert native state through a debug-only `__test_*` Tauri command. Headless is not available for WebView2 windows; run E2E only at milestones (owner rule: no visible windows during normal work), optionally on a second virtual desktop.

### B6. Accessibility in WebView2
- `@axe-core/webdriverio` `AxeBuilder({ client: browser }).analyze()` injects into frames; cannot reach iframes inside shadow DOM ([WDIO axe docs](https://webdriver.io/docs/accessibility-testing/axe-core); [npm](https://www.npmjs.com/package/@axe-core/webdriverio)).
- **Rec:** run axe in the same WDIO suite on every main screen (timeline, media bin, export dialog, settings) in dark and light; fail on serious/critical. For fast checks during development, run axe via Vitest + jsdom/Playwright against the UI served by Vite (no Tauri needed), since the UI is a normal web app.

### C3. Editelier's own agent control channel (dev builds only)

Option A: adopt a Tauri MCP plugin (above). Option B: our own minimal **JSON-RPC over a Windows named pipe**, compiled only with a `dev-automation` cargo feature, which also serves our WDIO tests (native frame hashes, timeline state, deterministic clock).

Security considerations (sources):
- Default named-pipe DACL grants **read to Everyone and anonymous**; restrict with the logon SID and deny `NT AUTHORITY\NETWORK` for local-only pipes ([Named pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights); [Named pipes overview](https://learn.microsoft.com/windows/win32/ipc/named-pipes)). Use `PIPE_REJECT_REMOTE_CLIENTS`; creating instances needs `FILE_CREATE_PIPE_INSTANCE`, and `FILE_FLAG_FIRST_PIPE_INSTANCE` lets the server fail if another process squatted the name ([CreateNamedPipeW](https://learn.microsoft.com/windows/win32/api/namedpipeapi/nf-namedpipeapi-createnamedpipew)).
- Do **not** use WebView2 `--remote-debugging-port` as the channel: it opens CDP to any local process and can be injected via env var, `AdditionalBrowserArguments` or registry policy ([WebView2 browser flags](https://learn.microsoft.com/microsoft-edge/webview2/concepts/webview-features-flags)); Chrome 136 restricted the switch because attackers used it to steal cookies ([Chrome blog](https://developer.chrome.com/blog/remote-debugging-port)); keep WebView2 at normal integrity ([WebView2 security](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)).
- P3GLEG's design is a good reference: refuse in release builds, random token in a sidecar file, constant-time compare, bounded request sizes ([repo](https://github.com/P3GLEG/tauri-plugin-mcp)).

**Rec:** Option B, behind three locks: (1) `#[cfg(all(debug_assertions, feature = "dev-automation"))]` so release binaries cannot contain it (CI/`ship-batch` check: `strings editelier.exe | grep -c editelier-automation` = 0); (2) opt-in at runtime (`EDITELIER_AUTOMATION=1`); (3) pipe `\\.\pipe\editelier-automation-<pid>-<random>` with `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, DACL = current user SID only, plus a per-session 256-bit token written to `%LOCALAPPDATA%\Editelier\automation.token` (user-only ACL, deleted on exit). Methods are a fixed allow-list (`open_project`, `seek`, `play/pause`, `get_state`, `render_frame_hash`, `export`, `screenshot_viewport`) — no `eval`, no arbitrary file paths outside a test workspace, size-bounded inputs validated with `serde` strict structs. A thin stdio MCP shim (Node or Rust, dev-dependency) can expose the same allow-list to Claude. Run `security-review` when it lands.

## Recommendations

1. Rational time (`num/den` + per-stream timebase) in the core from day one; PTS-keyed sample-and-hold so VFR is preserved on the timeline and conformed only at export.
2. Decode seek = keyframe seek + decode-forward to exact PTS; honour edit lists on import, write none on export (`+faststart`, zero-based PTS, closed GOP).
3. Linear-light Rec.709 f16 working space in wgpu; tag-driven 601/709 + range conversion; own BT.2390 HLG/PQ→SDR tonemap in WGSL; explicit colour tags on every export.
4. 48 kHz f32 mix; `ebur128` crate for integrated LUFS + true peak; presets −14 LUFS/−1 dBTP (social) and −23/−1 (R128).
5. Export presets as data files with source URL + verified date; YouTube numbers are official, TikTok/Instagram need a re-check before shipping.
6. Test pyramid: Rust oracle tests vs ffmpeg/ffprobe (framemd5, PTS, tags) per change; golden frames (Δ ≤ 2/255 + SSIM ≥ 0.995) per change to render code; VMAF ≥ 93 mean gate and perf budgets at milestones.
7. Synthetic committed fixtures + fetched CC0/CC BY media with a hashed manifest; never commit Pexels media.
8. E2E: WebdriverIO + `@wdio/tauri-service` (auto msedgedriver) + `@axe-core/webdriverio`, milestone-only; axe on the Vite-served UI for fast checks.
9. Profiling: `tracing` + `tracing-tracy` + `wgpu-profiler` behind features; PresentMon/PIX/WPR for investigations only.
10. Claude tooling: install nothing now; trial one Tauri MCP (hypothesi or P3GLEG) dev-only once the shell exists; build our own locked-down named-pipe JSON-RPC automation channel for tests.

## 10-line summary

1. Time: rational `num/den` + per-stream timebases (OTIO model); seek to keyframe then decode forward to exact PTS; honour MP4 edit lists on import, write none on export (YouTube forbids them).
2. VFR: preserve on timeline via PTS sample-and-hold, badge on import, conform to CFR only at export (Premiere/Resolve both push users to transcode first; we can do better).
3. Colour: linear-light Rec.709 f16 in wgpu, tag-driven BT.601/709 + full/limited range, own BT.2390 HLG/PQ→SDR tonemap, always write BT.709 tags (YouTube converts full→limited).
4. Audio: 48 kHz f32; `ebur128` (MIT, Tech 3341/3342-compliant) for LUFS + true peak; presets −14 LUFS/−1 dBTP social, −23/−1 R128; no official YouTube/TikTok/IG LUFS spec exists.
5. Presets: YouTube official (1080p 8/12 Mbps, 4K 35–45/53–68, AAC 48 kHz 384k, closed GOP); TikTok/IG 1080×1920 ≥30 fps H.264, bitrates not officially published; store presets as data with source + date.
6. Tests: ffmpeg/ffprobe oracle (framemd5, PTS, tags) per change; golden frames Δ≤2/255 + SSIM≥0.995; VMAF mean ≥93 (≈6 pts = 1 JND) and perf budgets (tracing-tracy, wgpu-profiler) at milestones only.
7. E2E: WebdriverIO `@wdio/tauri-service` auto-matches msedgedriver (Windows/Linux only); axe via `@axe-core/webdriverio`; WebDriver can't see the wgpu canvas, so expose debug frame hashes.
8. Media: self-generated ffmpeg fixtures committed; Blender CC BY, raw.pixls.us CC0 (check per file), Xiph derf (per-clip) fetched via hashed manifest; never commit Pexels (redistribution limits).
9. Claude tools: install nothing now; later trial ONE dev-only Tauri MCP (hypothesi MIT, popular but undocumented auth; or P3GLEG MIT, token auth + release-build refusal); skip ffmpeg/Windows/WDIO MCPs and community Tauri skills.
10. Own control channel: JSON-RPC over named pipe, debug+feature-gated, env opt-in, user-SID DACL, reject remote, first-instance flag, token, fixed allow-list; never use WebView2 `--remote-debugging-port`.
